本文以 Model Context Protocol（MCP） 為核心，系統性探討如何將 AI 大型語言模型與 土木工程大型分析軟體深度整合。文章涵蓋 MCP 的定義與三層架構原理、土木工程自動化的應用優勢、 透過 Claude Project 進行知識庫協作的完整設定方法，並以 ETABS 結構分析軟體為具體實作案例，示範 MCP 的組成設計、 導入流程與工程師日常使用方式。

Section 01

MCP 的定義

Model Context Protocol（MCP，模型上下文協議） 是由 Anthropic 提出的開放標準協議，目的是在 AI 大型語言模型（LLM）與外部資料來源、 工具及服務之間，建立一套標準化的雙向通信橋樑。

傳統上，AI 助手的能力受限於訓練資料的靜態知識，無法主動操作外部軟體或即時存取工程模型。 MCP 打破了這道邊界——它讓 AI 不只是「回答問題的助手」，而是能夠 直接驅動工程軟體執行計算、提取數據、修改模型的數位協作夥伴。

對土木工程師而言，MCP 的意義在於： 只需以自然語言下達指令（例如「分析所有梁的應力比並標記超載元素」）， AI 便能透過 MCP 自動完成原本需要數小時手動操作的工作流程。

📐
MCP 採用 JSON-RPC 2.0 作為通信格式，並從語言服務器協議（LSP）汲取靈感， 以相同的標準化思路，將 AI 整合至工程軟體生態系統的每個角落。
Section 02

MCP 的組成架構

MCP 採用主機－客戶端－服務器（Host-Client-Server）三層核心架構。 這種設計在傳統 C/S 架構基礎上引入了「主機」協調層，使 AI 大模型得以統籌調度多個工程軟體並行執行任務。

🖥️ MCP 主機 Host  ——  AI 對話介面（Claude）
● 接收自然語言指令 ● 編排任務計劃 ● 跨客戶端上下文聚合 ● 大模型整合與採樣
↕ JSON-RPC 2.0
🔗 MCP 客戶端 Client  ——  主機內部業務進程
● 維持 1:1 有狀態會話 ● 協議版本協商 ● 雙向消息路由 ● 訂閱與通知管理
↕ COM / REST / SDK / gRPC
⚙️ MCP 服務器 Server  ——  外部服務代理閘道
🔧 工具 Tools — 可執行的操作命令 📊 資源 Resources — 可讀取的數據上下文 📝 提示語 Prompts — 可重用的任務模板
↕ API 調用
🏗️ 目標工程軟體  ——  ETABS / ANSYS / SAP2000…
● 執行結構計算 ● 返回分析結果

主機（Host）——「大腦」

主機是工程師與 AI 大模型直接交互的終端，例如 Claude 對話介面或 AI 編輯器。 它負責創建並管理多個客戶端進程，掌控連接權限與生命周期， 並承擔大模型集成、自然語言理解及跨客戶端的上下文聚合等核心任務。

客戶端（Client）——「秘書」

客戶端「寄生」於主機內部，是主機與服務器之間的通信橋樑。 每個客戶端與特定 MCP 服務器維持 1:1 的獨立有狀態連接， 負責協議協商、雙向消息路由，以及追蹤多步驟工作流程的執行狀態 （例如記住「第 3 次迭代後梁斷面已改為 H400×200」）。

服務器（Server）——「執行手」

服務器是運行在主機之外的獨立程序，透過軟體 API 直接操控目標工程軟體。 它提供三種核心能力：

🔧

工具 Tools

可執行的操作命令，如連接軟體、執行分析、修改斷面、匯出報表。對應軟體 API 的函式調用。

📊

資源 Resources

可讀取的數據上下文，如模型幾何、材料屬性、分析結果數據集，供 AI 進行推理與判斷。

📝

提示語 Prompts

可重複使用的任務模板，如「迭代優化」、「自動出報表」，讓工程師直接套用常見工作流。

Section 04

Claude Project 協作設定

Claude Project 是在 Claude.ai 平台中建立的長期協作專案空間， 讓工程師能夠將 MCP 知識庫、操作規範與工作指令集中管理， 使 AI 在每次對話中都具備完整的工程背景知識，無需重複說明前提。

4.1 建立 Project 的基礎設定

  • 1

    登入 Claude.ai，在左側欄點擊「New Project」，命名為「ETABS MCP 自動化」或對應的工程專案名稱。

  • 2

    進入 Project 設定頁面，確認使用的模型版本（建議選擇 Claude Sonnet 或以上版本以獲得最佳推理能力）。

  • 3

    在 Project 內進行的所有對話將共享同一組 Project Knowledge 與 Custom Instructions，形成一致的工作環境。

4.2 Project Knowledge（知識庫）

Project Knowledge 是上傳至 Project 的靜態參考文件， AI 在每次對話時都能查閱這些知識作為背景。 對土木工程 MCP 協作而言，應上傳以下類型的文件：

📂 Project Knowledge 建議上傳內容

① MCP 架構知識庫——本文所描述的 Host-Client-Server 三層架構說明，作為 AI 撰寫 MCP 文件的格式依據。

② 目標軟體 API 文件——例如 ETABS API 指導綱要、CSI 官方 API 手冊摘要，使 AI 能掌握正確的函式名稱與參數規格。

③ 已完成的 MCP 文件範本——如前述 ETABS API MCP 架構知識庫文件，作為後續撰寫的品質參照標準。

④ 法規與設計規範摘要——如 ACI 318、AISC 360 重點條文，供合規檢查工作流使用。

4.3 Custom Instructions（自訂指令）

Custom Instructions 定義了 AI 在此 Project 中的角色定位、行為規範與輸出格式要求， 是確保每次對話品質一致的核心機制。以下是針對土木工程 MCP 協作的完整 Custom Instructions 結構：

Section 05

ETABS 實作案例

以下以 ETABS v21 結構分析軟體為例， 完整示範 MCP 的組成設計、導入設定與日常使用方法。 ETABS API 採用 Windows COM（組件對象模型）介面， 透過 Python 的 pywin32 庫（win32com.client）與本地 ETABS 進行通信。

⚠️
API 文件聲明：本案例基於 ETABS API Beginner Guide 2025 撰寫。 所有函式名稱、參數規格請以 CSI 官方 API 文件（ ETABS 安裝附帶）為最終依據。

5.1 ETABS MCP 的三層組成

主機（Host）

Claude AI 對話介面作為主機。工程師輸入自然語言指令後， 主機解析意圖、編排工具調用序列，並彙集來自 ETABS 的分析結果以生成工程報告。

客戶端（Client）

客戶端寄生於主機內，與 ETABS MCP 服務器維持連接狀態。 關鍵作用在於追蹤迭代優化的中間狀態 （例如第幾次迭代、哪些元素已調整斷面），確保多步驟工作流不中斷。

服務器（Server）

服務器透過 COM 介面連接本地 ETABS，提供以下三類能力：

工具（Tools）——可執行操作

工具名稱 對應 ETABS API 功能說明 返回值
connect_etabs GetActiveObject / Dispatch 連接或啟動 ETABS，初始化 SapModel 連接狀態、版本號
unlock_model SetModelIsLocked(False) 解鎖模型以允許修改操作 ret（0=成功）
get_frame_sections PropFrame.GetNameList() 獲取所有已定義的梁柱斷面名稱 斷面名稱陣列
get_frame_elements FrameObj.GetNameList() 獲取所有框架元素（梁、柱、斜撐） 元素名稱陣列
run_analysis Analyze.RunAnalysis() 執行結構分析計算 ret（0=成功）
get_results Results.* 提取分析結果（內力、位移、反力） 結果數據集
modify_section PropFrame.SetRectangle() 等 修改元素斷面屬性（用於迭代優化） ret（0=成功）
close_etabs ApplicationExit() 安全關閉 ETABS，釋放 COM 資源 關閉狀態

資源（Resources）——可讀取數據

  • 模型基本信息：程序版本GetProgramVersion()、單位系統、全局座標設定
  • 元素幾何數據：節點座標、框架元素起終點、面元素邊界定義
  • 斷面與材料屬性：幾何參數（寬、高、厚度）、材料彈性模量與強度
  • 分析結果數據集：各荷載組合下的節點反力、元素端部彎矩/剪力/軸力、層間位移角

提示語（Prompts）——工程任務模板

  • 自動化出報表提取所有荷載組合下的柱軸力，整理成表格，標記超過設計容量 80% 的元素
  • 迭代優化執行分析 → 檢查梁應力比 → 若超過 0.9 則斷面升一級 → 重新分析，直到全部合規
  • 數據驗證對比手算與 ETABS 輸出的基底剪力，允許誤差 ±5%，超出則報告差異

5.5 完整工作流示例：迭代斷面優化

🖥️ 主機（Host） Claude AI 接收指令：「優化所有柱斷面，應力比 ≤ 0.85」
↓
🔗 客戶端（Client） 建立有狀態會話，追蹤迭代進度，路由工具調用序列
↓
⚙️ 服務器（Server） COM 介面 Step 1：unlock_model
↓
⚙️ 服務器（Server） Step 2：run_analysis → Analyze.RunAnalysis()
↓
⚙️ 服務器（Server） Step 3：get_results → 提取所有柱的應力比
↓
🔗 客戶端（Client） 判斷：所有應力比 ≤ 0.85？
↓ 若否，回到 Step 2（最多 20 次）
⚙️ 服務器（Server） Step 4：modify_section → 超標柱斷面升一級
↓ 收斂後
🖥️ 主機（Host） 回報工程師：迭代次數、各柱最終斷面、應力比清單
迭代優化腳本（完整版）
import win32com.client

# ── 連接 ETABS ──
try:
    myETABSObject = win32com.client.GetActiveObject(
        "CSI.ETABS.API.ETABSObject"
    )
except:
    myETABSObject = win32com.client.Dispatch(
        "CSI.ETABS.API.ETABSObject"
    )

SapModel = myETABSObject.SapModel
SapModel.SetModelIsLocked(False)

# ── 迭代優化參數 ──
STRESS_RATIO_LIMIT = 0.85   # 應力比上限
MAX_ITERATIONS    = 20      # 最大迭代次數（終止條件）
iteration         = 0
converged         = False

while iteration < MAX_ITERATIONS and not converged:
    iteration += 1
    print(f"\n── 迭代第 {iteration} 次 ──")

    # Step 1：執行分析
    ret = SapModel.Analyze.RunAnalysis()
    if ret != 0:
        raise Exception(f"分析失敗，錯誤代碼：{ret}")

    # Step 2：提取結果（此處為示意，實際函式依 API 文件）
    [ret, elem_names] = SapModel.FrameObj.GetNameList()
    if ret != 0:
        raise Exception(f"元素清單取得失敗：{ret}")

    # Step 3：檢查應力比（示意）
    violations = []
    for name in elem_names:
        stress_ratio = get_stress_ratio(SapModel, name)
        if stress_ratio > STRESS_RATIO_LIMIT:
            violations.append(name)

    # Step 4：判斷是否收斂
    if len(violations) == 0:
        converged = True
        print(f"✅ 收斂！所有元素應力比均 ≤ {STRESS_RATIO_LIMIT}")
    else:
        print(f"⚠️  {len(violations)} 個元素超標，升級斷面中...")
        for name in violations:
            upgrade_section(SapModel, name)

# ── 發散處理 ──
if not converged:
    print(f"❌ 達到最大迭代次數 {MAX_ITERATIONS} 次，設計未收斂，請人工複核。")

# ── 資源釋放（必須執行）──
myETABSObject.ApplicationExit()   # 關閉 ETABS 實例
myETABSObject = None               # 釋放 COM 物件引用
print("連接已關閉，資源已釋放。")

5.6 使用注意事項

🪟
僅支援 Windows 平台
ETABS COM 介面為 Windows 專屬技術，無法在 macOS 或 Linux 上運行
🔑
必須持有有效授權
COM API 功能整合於已授權的 ETABS 核心程序，無授權版本無法使用
✅
所有 API 調用必須驗證返回碼
ret ≠ 0 表示失敗，必須捕獲並記錄，不得忽略
🔓
修改前必須解鎖模型
呼叫 SetModelIsLocked(False) 後才能進行任何修改操作
🧹
腳本結束時必須釋放資源
未執行 ApplicationExit() 將導致 ETABS 在背景持續占用記憶體
📖
API 函式名稱以官方文件為準
本文所列函式名稱以參考文件為依據，正式使用前請查閱 CSI 官方 API 手冊
Section 06

結論與建議

本文系統性地探討了 MCP 協議在土木工程專業軟體自動化領域的應用潛力， 從架構原理到 Claude Project 協作設定，再到 ETABS 的完整實作案例， 可歸納出以下核心結論與分階段導入建議。

6.1 核心結論

01
MCP 是工程 AI 整合的關鍵基礎設施

MCP 的三層架構（Host-Client-Server）提供了一套語言無關、軟體無關的通用橋接標準，使 AI 大模型得以透過統一協議驅動 ETABS、ANSYS、SAP2000 等異質工程軟體，徹底解決了 AI 與專業工具之間的整合碎片化問題。

02
自然語言成為新的工程操作介面

透過 MCP，工程師無需學習 API 語法或撰寫腳本，僅需以自然語言描述任務目標，AI 即可自動規劃並執行多步驟工作流。這從根本上降低了工程自動化的技術門檻，讓非程式背景的土木工程師也能受益。

03
Claude Project 是知識管理的有效載體

將 MCP 架構知識庫、API 文件摘要與 Custom Instructions 集中於 Claude Project，使每次對話都能在一致的工程知識背景下進行。這種「知識即配置」的協作模式，大幅縮短了工程師與 AI 之間的溝通成本。

04
效益顯著但需正視技術前提

ETABS 案例驗證了 MCP 可節省 40% 例行工時並提升 2–3 倍生產力，但成效高度依賴 API 文件的完整性、返回碼的正確處理，以及資源釋放流程的嚴格執行。技術基礎不牢固將導致腳本不穩定。

6.2 分階段導入建議

Phase 1
基礎建置期（第 1 個月）
  • 確認目標軟體的 API 介面類型（COM / REST / SDK），取得官方文件
  • 建立 Claude Project，上傳 MCP 架構知識庫與 API 文件摘要
  • 設定 Custom Instructions，定義 AI 角色與禁止事項
  • 完成連接初始化測試，驗證 GetProgramVersion() 等基礎調用
Phase 2
應用測試期（第 2–3 個月）
  • 選擇 1–2 個高重複性工作流作為測試點（建議從「自動出報表」起步）
  • 建立標準提示語模板庫，積累 Project Knowledge
  • 針對常見錯誤碼建立處理查詢表，完善錯誤回報機制
  • 收集工程師使用回饋，迭代優化 Custom Instructions
Phase 3
全面推廣期（第 4 個月起）
  • 擴展至迭代設計優化、法規合規檢查等複雜工作流
  • 探索跨軟體整合（如 ETABS → Revit 的 BIM 數據交換）
  • 建立組織級的 MCP 知識庫，系統化沉澱工程自動化經驗
  • 評估導入 CI/CD 概念，將關鍵工作流納入版本控制管理
